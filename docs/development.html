01定位与证据链

一句话定位：纯 MoonBit 的 iCalendar（RFC 5545）解析 / 重复事件展开库，附带最小 CalDAV（RFC 4791）服务端。计算限定为支持的规则与可靠固定时区，不承诺完整协议栈或任意来源的语义处理。

立项调研记录（2026-09-08；不是今日全生态排名或提交稿）：

  • 生态空位：mooncakes.io 检索 caldav / webdav / webcal / calendar-import 均返回 No modules found。
  • 五家竞品全是离线库：mooncal、mooncalguard、rrule_lab、moon-schedule、moonrrule 输入均为调用方喂好的字符串；mooncal 明言「不做 CalDAV 网络同步」「文件输入不属于 0.1.2 范围」。调研期间已按五道工序逐包核实。
  • 评委口径：2026-09-08 评委确认「CalDAV 这个选题没问题」。
  • 业界参照：Python 的 Radicale 证明「只实现到各家客户端能理解为止」的最小 CalDAV 服务端路线可行；vdir「一文件一项」是跨工具互认的存储约定。
当时调研的差异：① 端到端——从网络取件到客户端可连，而非纯计算库；② 真实数据——RFC 5545 附录 A 对拍 + 真实客户端联调矩阵，当时调查的 fixture 情况不代表全部外部数据能力；③ RECURRENCE-ID 单实例改期合并——五家共同空白（调研矩阵 ④b 行）。

设计立场：保真优先——未知组件/属性一律保留（竞品 mooncal 是固定字段清单）；时间四态显式建模；类型化计算不能完成时失败；组件树保留不等于所有数据可计算。这三条是后续所有包必须继承的基线。

05每步工作流（Definition of Done）

每个里程碑严格走同一循环，禁止「先写一大坨再补测试」：

  1. 写测试先行或同步：每块新行为至少一个 assert_eq / assert_true(pattern is …) 级别的断言测试；边界（空输入、畸形输入、行号）必须覆盖。
  2. 实现：块式组织，///| 分隔，每块带一句话文档注释说明「为什么」。
  3. 验证链：moon fmt && moon check && moon test && moon info，然后检查 .mbti diff——接口变化必须是预期内的，意外的 diff 说明改坏了边界。
  4. 提交：一次提交一个里程碑，消息格式 S<n>: <一句话>，正文列改动点 + 验收证据（测试数、对拍结果）。命令必须是 git -c core.hooksPath=.githooks commit …——项目钩子会跑 moon check 并拒绝「改源码但不更新 PROGRESS.md」的提交。
  5. 更新跟进文档：docs/PROGRESS.md（跨会话状态源：本地文件，不入库——§1 快照、§2 里程碑、§3 会话日志）与本手册 §02/§04/§07。钩子会校验它在上次提交后被更新过。
规模红线：单步新增代码超过计划规模 1.5 倍（如 S1 超过 ~220 行）即视为范围蔓延——停下来检查是不是把下一步的活提前做了，砍回去。
验收有效性红线（S10 复盘，见 §11）：本循环第 1 条「至少一个断言测试」不足以构成验收。凡「接收输入并据此决定输出」的操作，必须额外满足 §11 的 R1–R7——尤其 R1（一对只差输入的请求必须给出不同结果） 与 R2（选择类操作必须有空结果用例）。只断言「预期的东西回来了」的用例不算证据：全量返回同样能通过它，S10 的两条缺陷就是这么漏过全部闸门的。

06MoonBit 工程约定与踩坑清单

新格式（rr_moon_mod + rr_moon_pkg）下的硬规则，违反即编译失败或静默 bug：

  • 导入只写 moon.pkg：import { "moonbitlang/async/http" @http } 写在所在目录的 moon.pkg；.mbt 文件里写 import "..." 是硬错误（3001/3002）。测试专用导入用 import { … } for "test"。
  • 可抛错误类型：pub(all) suberror Name { Ctor(field~ : Type) }；Error 是内建 opaque 类型不是 trait，impl Error for X 必失败。展示用 pub impl Show for Name with fn output(...)。
  • 带标签字段两头都要带：构造 Ctor(a=1, b=2)，匹配 Ctor(a=x, b=y)；位置式会报 requires 0 positional arguments。
  • 区间：a..<b（右开）/ a..<=b（闭）。旧写法 a..=b 语义等价，但新版 formatter 会归一成 a..<=b；for 头写坏会在下游报假错误（unbound identifier / 类型不匹配）——先修 for 头。
  • 不要 String::trim() 接 StringView::data()：data() 返回整个原串不是切片，trim 会静默消失。参照当前 ical/text/content_line.mbt 的 StringView 切片与 to_owned() 所有权边界。
  • API 拿不准先查：moon ide doc "Type::method"（搜 core + 已注册依赖），不要凭记忆写 stdlib 名字。
  • async 入口：async fn main 需要根包 moonbitlang/async 一并导入；可执行包声明 pkgtype(kind: "executable")。
  • Int 与 Int32 是同一个类型：新版 formatter 把源码里的 Int 归一成 Int32；moonc v0.10.15 及以前 .mbti 会归一回 Int，v0.10.17 起直接渲染 Int32（全仓 6 个接口文件 24 行纯渲染 diff，已随 S10.5 入库）——语义完全不变。S10 后仓库源码统一为 Int32，新代码跟随现状即可。
  • 源码里的可选参数是带标签参数：新版 formatter 把 name? : T = d 改写成 name~ : T = d。差别在调用方式——~ 形式只能按名字传（f(x, name=1)），不能再按位置传（实测 parse_date_time(line, zones, 7) 报「requires 2 positional arguments, but is given 3」）。仓库内所有调用点都用 name=value，故本次迁移零调用点改动。
  • .mbti 分不清 ? 与 ~：两者在接口文件里都渲染成 name? : T。于是「.mbti 无 diff ⇒ 对外接口无变化」这条判据在新工具链下有盲区——S10 迁移 .mbti 零 diff，但按位置传可选参数的调用方会编译失败。判断接口兼容性时不能只看 .mbti。
  • 默认关闭的新 lint：新版引入了一批默认 off 的检查（0073 unnecessary_annotation、0074 missing_doc、0038/0039 证明类等），--deny-warn 不会开启它们。用 moon check --warn-list "+74" 之类的开关按需排查（编号见 moon explain --diagnostic）。

07上游接缝登记（活文档）

当前实现与历史接缝更正见 docs/upstream-seams.md。上游补齐后先验证契约，不承诺“一行切换”。

接缝当前实现与边界
native 文件 / HTTP 服务ical/store、ical/fetch 与 cmd/serve 限定 native；没有 js_shim、localStorage 或 Fetcher 后端。
时区ZoneTable 仅计算可靠固定绑定；无 IANA tzdb，也未实现动态 VTIMEZONE 转换。这是两项独立能力，不能以无 tzdb 推断内嵌转换不能实现。
WebDAV 方法cmd/serve 接受裸 TCP，ical/httpd 手解析任意方法 token 并写响应。S5 实测 ServerConnection Reader 是帧化 body，不能当原始请求流；未使用 send_response/end_response 或外部 XML 库。
取件超时ical/fetch/fetch.mbt 自行 with_timeout；本地永不响应监听器守卫见 fetch_test。S20/S21 的上游无超时核查有版本范围，升级需重查。

08明确不做（边界）

  • CalDAV 客户端——只做服务端；客户端行为由 Thunderbird/DAVx5 承担。
  • 云平台同步适配——不接 Google Calendar OAuth、iCloud/Yahoo 账户或 Outlook/Microsoft Graph；均列为赛后方向。
  • iTIP/iMIP 会议邀请、参会人状态、协作流程。
  • ACL 权限体系——首版无认证（localhost 演示），TLS 留赛后。
  • IANA tzdb / 动态 VTIMEZONE 转换——仅可靠固定绑定可计算，地域 TZID 无显式绑定与动态/无效/冲突引用报错。原始声明可保留，不等于支持时间语义（接缝 S2）。
  • chunked 请求体——回 411 Length Required（没有增加该能力的实测需求证据）。
  • 超大 .ics 流式解析、sync-token 全量同步（不声称已有 CTag 支持）。
  • DAV:prop 选择的剩余边角——S34 让 PROPFIND/REPORT 尊重属性选择（裁剪 + 404 propstat + propname + 畸形体 400）；仍按 local name 匹配（命名空间不敏感）、404 回显带 DAV: 前缀（形状解析器只留 local name）、calendar-data 的子元素（expand 等）不支持而回全量、allprop 的 include 读为无额外约束。
  • MKCALENDAR 请求体属性——S10 让 MKCALENDAR 真正建集合，但 body 里的 displayname / calendar-color 等属性不落盘；集合名即 displayname。
  • /cal/ 兼作家目录与默认集合——S10 刻意的兼容取舍：首版已从 /cal/ 直接服务事件且既有客户端按该路径配置，故新建集合并排放在其下（/cal/<cal>/），而不是把事件搬进 /cal/default/。
  • VALARM 的 time-range——回 403 supported-filter，不解析相对 trigger。
  • RDATE PERIOD / 任意时间域组合——DATE/DATE-TIME 已支持集合合并；PERIOD、缺 DTSTART 的重复及跨 DATE/floating 域的 RID/override 拒绝。不是完整 RFC 合法组合支持。
  • 请求 timezone 转换——只检查已实现结构/字段，非法为 403 valid-calendar-data；存在时 temporal 判断保守失败（500），文本筛选可运行。不声称完整验证 observance RRULE。
  • 非 VEVENT 重复计算——重复 VTODO 等时间查询失败；非重复 VTODO 采用 RFC 4791 §9.9 表。
  • 查询预算——10000 生成周期或 CalDAV 4096 原始实例预算内不能证明结论时失败；不保证所有合法远期/稀疏查询都能完成。period 预算不足包括有界与零输出，不把部分结果当完整空集。
  • RRULE 第三档（BYWEEKNO/BYYEARDAY/BYHOUR 系/SECONDLY/MINUTELY）——显式报错拒绝，不静默吞。

11验收有效性：为什么缺陷能过验收（S10 复盘）

背景：0.2.0 发布、进入验收后被指出两条缺陷——「calendar-query 忽略 filter，关键语义缺失」与「MKCALENDAR 不建集合」。两条都属实，却在此前所有闸门全绿的情况下漏过：全目标测试、S5/S6 活体验收、Thunderbird 真实联调、96% 覆盖率，没有一项报警。本节记录根因，并把它固化成规则，避免再犯。

一句话根因：验收断言的是「有没有回预期的东西」，而不是「输入有没有改变结果」。在「忽略输入」与「遵守输入」两种实现下，前者同样能让断言通过——于是断言不具判别力，闸门形同虚设。

根因

#根因当时的证据
1断言不判别（最直接原因）：用例的请求体里根本不含被检验的输入S6 的 calendar-query 请求体没有 <C:filter>，断言是 code == 207 and "UID:s6@moon-ical" in body——只要「把已知存在的事件返回」就通过，全量返回同样满足。该用例在「正确实现」与「完全不实现」两种情况下都是绿的。
2能力声明先于证据README Features 与 §02 把 MKCALENDAR 列为已支持，而全仓（单测 + S5 + S6）零个 MKCALENDAR 用例。声明来自「路由里有个分支回 201」，不是来自任何被验证过的行为。
3验收按「协议动作清单」组织，而非「语义契约」S6 的 11 项按 OPTIONS/PROPFIND/REPORT/PUT/DELETE 排列，每项只问「有没有回预期状态码」。一个回 207 的桩实现能通过状态码清单。
4全为正例，没有否定例与前置条件例11 项里没有任何一项形如「这个输入必须不返回那个」；403 的 valid-filter / supported-filter 两条前置条件从未被触发过一次。
5客户端互操作被当成协议完整性S7 的 Thunderbird 全绿，是因为它只用单一内建集合、也不依赖服务端时间范围过滤——恰好绕开了这两条缺陷。互操作只证明「该客户端走的那几条路」，不等于协议面完整。
6边界清单只有「有意不做」，没有「已声明但未验证」§08 列的是刻意的省略（tzdb、scheduling、TLS…）。两条缺陷不在其中，于是被隐式当成「已支持」；没有任何机制强制「文档能力 ↔ 证据」的映射。
7「规范机械对拍」只在库层做了，协议层没做RRULE 层从第一天就用 graham 语料机械抽取 40 条串对拍，这条纪律确实有效（第一/二档全部对拍通过）；CalDAV 层没有等价的「从 RFC 例子机械抽取请求体」，请求体全部手写，于是继承了实现者的盲区。

硬性规则（并入 §05 的 Definition of Done）

#规则判定方式
R1判别性断言：任何「接收输入并据此决定输出」的操作，验收必须包含一对只差该输入的请求，并断言两者结果不同calendar-query：同一集合上两个只有 time-range 不同的 query 必须返回不同的资源集合。
反例（禁止）：只断言「已知事件出现在响应里」。
R2选择 / 过滤类操作必须有「空结果」用例断言返回空 multistatus，而不是「返回了全部」。区间外、无匹配属性都必须有此例。
R3可拒绝的操作必须有拒绝用例，并断言具体状态码 + 具体错误元素如 403 + <C:valid-filter/>；不能只断言「不是 200」。每条新增的 403/405/409 路径都要有落点。
R4每条对外声明的能力必须有至少一个「因它缺失而失败」的检查做不到就把它从 Features 移进 §08 边界。落地载体 = 下文的「能力 → 证据矩阵」：改能力声明必须同步改矩阵。
R5协议请求体从 RFC 例子机械抽取，与 RRULE 层的 graham 语料同纪律手写请求体只允许作为补充；抽取脚本或逐条抄录都要在用例注释里留下出处（RFC 章节号）。
R6互操作报告必须写明「该客户端未触及的协议面」互操作通过不得用作协议完整性的证据；矩阵要有一列记「未覆盖」。
R7里程碑验收标准必须写成可判否形式「REPORT 序列全绿」不合格；「同一集合上两个只有 time-range 不同的 query 返回不同集合」合格。
