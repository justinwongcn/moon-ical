06逐项卡片

下列卡片可用上方按钮按语言筛选、按输入框搜索。每张卡只写本轮取到一手证据的内容； "缺口"一栏优先抄项目自己承认的短板。

icalendar Python

解析 / 编解码 · 事实标准 · 文档版 7.3.0 · BSD-2
  • 自称"RFC 5545 兼容的解析器与生成器"，依赖 python-dateutil 与 tzdata
  • 时区后端可插拔：zoneinfo / dateutil.tz / pytz 三者皆支持
  • 官方 RFC 支持表：5545 · 6868 · 7529 · 7953 · 7986 · 9074 · 9253（2445 视为被取代）；反向清单：6321 xCal、6350 vCard、9073 部分
  • 未知 / X- / IANA 组件由 ComponentFactory 动态建模并全量保留
  • RFC 7986 的 COLOR、5545 §3.2.10 的 LANGUAGE 参数有专门实现
缺口 递归展开不在其内；属性是字典式取用（event.get('DTSTART').dt），官方示例明示不校验合规性

ical（allenporter） Python

解析＋展开一体 · 需 Python 3.11+ · 被 Home Assistant 采用
  • 核心卖点：递归展开内置，cal.timeline 直接给出已展开、按时间排序的实例序列
  • 支持 RFC 5545 · 6868 · 7986 · 8536（TZif），有专门的时区与自定义 TzInfo 技术指南
  • ical.store.EventStore：应用层状态管理（保证时区正确、编辑递归单实例）——本轮唯一见得的库内 store 层
  • 异步拉取远程 .ics：calendar_from_url（可选 [async] extra，复用 aiohttp session 连接池）
  • strict mypy + 输入校验与明确错误类型（CalendarParseError）
缺口 不支持旧 Python（3.8+ 的 icalendar 才行）；jCal / 底层原始组件控制不如 icalendar

recurring-ical-events Python

递归展开 / 查询层 · 3.8.2 · LGPL-3.0 · NLNet 资助
  • 逐条自报 DONE 清单：DST、无限递归、结束递归、多 RRULE、RDATE、EXDATE、DURATION、RECURRENCE-ID + THISANDFUTURE、X-WR-TIMEZONE、开始为 date 与为 datetime 两种形态
  • 查询式 API：of(cal).between() / .after() / .at()，可指定 components=["VTODO","VJOURNAL","VALARM"]
  • 分页续查：next_page_id 可交给下一个请求继续 —— 面向 Web 服务的设计
  • 坏数据策略：skip_bad_series=False 默认抛错（如 BadRuleStringFormat: UNTIL parameter is missing），True 则整条序列跳过
  • 架构对扩展开放：可自定义 ComponentAdapter / Series / Occurrence / CalendarQuery
缺口（自陈） 非格里高利历递归 = TODO（RFC 7529、RFC 7953 均挂 issue）；EXRULE 明确不做（规范已废弃）

ics.py Python

解析 / 生成 · 面向"不想读 RFC 的人"
  • 目标明确写在名字里：不要求使用者懂 iCalendar，也能读写 .ics
  • 有 Event / Calendar / Alarms / Timeline 四类 API，另有 Low-level Container 与自定义属性出口
  • 文档专设 "Known Limitations" 与 "Missing support for…" 两节，并讨论带/不带时区的 datetime 比较这一坑
缺口 递归未支持（issue #14 中作者直言难点在于"既要表达、又要解析、还要给出 Pythonic 写入口"）；第三方称其自 0.7.2（2021-08）后无稳定版发布

python-dateutil Python

递归算法底座 · 被 icalendar 依赖 · 被 Go 移植
  • 本轮定位为"递归层的事实底座"：icalendar 把它列为依赖，Go 的 rrule-go 自称"对 dateutil.rrule 的部分移植"并称其 excellent
  • rrule / rruleset 是两语言共同的 API 形状来源
缺口 其文档页本轮取不到正文（JS 壳），逐参数细节标记为 ?，未据此下结论

vdirsyncer Python

双向同步 CLI · pimutils
  • 在多种服务端与本地目录之间同步日历与地址簿；本地端 type = "filesystem" ＋ fileext = ".ics"，远端 type = "caldav"
  • 冲突定义清晰：自上次同步后两边都改过的 item 即冲突
  • 冲突策略可配：null（报错不动）/ "a wins" / "b wins" / ["command","vimdiff"]（拉外部三路差异编辑器，临时文件传两边内容）
  • 自动发现流程：vdirsyncer discover 后 sync
缺口 冲突是整条 item 粒度取胜方，不做属性级合并

Radicale Python

CalDAV + CardDAV 服务端 · GPLv3 · 3.x
  • 分享日历与通讯录；支持事件、待办、日记与名片；开箱可用，数据存为简单目录结构
  • 增量同步：sync-token，max_sync_token_age 默认 2592000 秒（30 天）后作废旧 token；另有可选用子目录缓存 sync-token（≥3.3.2）
  • 两个"防 DoS 上限"配置：expanded report 的实例上限与 max_freebusy_occurrence（≥3.2.3）默认均 10000，超限返回 HTTP 错误而不是慢慢算完
  • skip_broken_item 容忍坏条目；TLS、反向代理接管身份、四类插件（认证 / 权限 / web / 存储）
  • ≥3.7.0 有 [sharing] 集合共享
缺口（自陈） "CalDAV 与 CardDAV 不是完美的协议，其主要问题是复杂度——所以我们决定不实现整个标准，只实现到能让各家客户端理解为止"；且"永远不会是客户端、永不做界面"

khal / ikhal Python

终端日历应用 · vdir 存储 · Python 3.10+
  • 读写 vdir，靠 vdirsyncer 与 CalDAV 服务器同步（应用与同步职责分离）
  • 快速新增事件的 CLI；ikhal 提供浏览＋编辑的交互 TUI
  • 被打包进 Debian / Arch / Nix / Homebrew / FreeBSD 等主流发行版
缺口（自陈） README 的标题就叫 "Features (or rather: limitations)"；明确写着"尚不支持编辑事件的时区"，且不支持 Windows

caldav（Python 客户端） Python

RFC 4791 客户端库
  • 取自 icalendar README 的自述："CalDAV is a RFC 4791 client library for Python based on icalendar"
  • 即协议层与表示层分离：客户端库骑在解析库上
缺口 细粒度操作支持本轮未逐项核实 ?

vdir 规范 磁盘约定

1.1.0 · 2025-03-31 · 独立发布的规范
  • 根目录 = 集合们；一个集合 = 一个子目录；一个 item = 一个文件，扩展名必须是 .ics（RFC 5545）或 .vcf
  • 文件须含恰好一个事件/任务/联系人；但递归例外事件允许多个 VEVENT
  • 一个文件内若有多个 UID，其值 MUST NOT 不同；文件名 SHOULD URL-safe（以便同步到 CalDAV 后保留）
  • 集合元数据 = 无扩展名的小文件：color（#RRGGBB，禁缩写与 CSS 名）、displayname、description、order；命名刻意对齐 WebDAV/CalDAV 属性
  • 写入 MUST 原子（临时文件 + rename；.tmp 与无扩展名文件读取时 MUST 忽略）；改动时 MUST 沿用原文件名
  • 自陈"目前 suffers from a rather major performance problem"，各家靠自建索引缓解
对 moon-ical 最可直接采用的一层：格式极简，实现它即接入整个终端 PIM 生态

arran4/golang-ical Go

解析 / 序列化 · 事实默认 · 零依赖
  • 9 类组件常量齐全（含 STANDARD / DAYLIGHT），并有 Required() 按 RFC 给出必填规则
  • 三档容错解析：严格 / SkipPropertyParser / FallbackParser(LooseParser)（保留 token+value、丢弃坏参数），并可写自定义 parser（如跳过 X-TKF-）；同一 parser 也作用于嵌套组件
  • ParseCalendarFromUrl；构造侧有 NewCalendar / NewCalendarFor(service) / NewCalendarWithOptions(WithVersion, WithProductId)
  • 递归：提供 GetRRules / GetExDates / GetRDates / GetRecurrenceID 与 ParseRecurrenceRule(...).String() 往返，但刻意不展开
  • VALARM：NewAlarm + AddVAlarm，含 DISPLAY 告警必填项的规范提醒与 TRIGGER 相对时长语义
  • 出席者/组织者：含 CalendarUserTypeIndividual、ParticipationStatusNeedsAction、ParticipationRoleReqParticipant、WithCN、WithRSVP 等参数化选项
缺口 展开需外接 rrule-go 且 RECURRENCE-ID 合并自己写；序列化默认 LF；README 末尾"Looking for a co-maintainer"

teambition/rrule-go Go

递归展开 · 该层事实标准 · MIT
  • 自述"对 iCalendar RFC 所记录递归规则的完整实现"，且是 python-dateutil rrule 模块的部分移植
  • 源码注释里自我描述为 "small, complete, and very fast"，含结果缓存；字段覆盖 bysetpos / bymonth / byweekday 等
  • API：NewRRule(ROption)、StrToRRule、StrToRRuleSet、All()、Between(a,b,inc)；Set 支持 RRule + RDate + ExDate 合并
  • 兼容"DTSTART 写在 RRULE 串里"的历史形态（OrigOptions 与 Options 分离）
  • 输出格式为 DTSTART:…\nRRULE:… 的字符串往返
缺口 版权标注 2017–2023；不做 .ics 解析、不做时区日历系统（靠传入 time.Time）

floatpane/go-icalendar Go

扁平模型 + 递归 + iMIP + 忙闲 · 需 Go 1.26+
  • 定位一句话："把 .ics 的低层属性袋变成可直接渲染的扁平 Event 结构，并补上邮件客户端本来要手写的那层调度胶水"
  • iMIP 全套：NewRequest / NewCancel（自动 bump SEQUENCE 并置 STATUS:CANCELLED）/ GenerateRSVP（METHOD:REPLY、只保留应答者、更新 PARTSTAT、RSVP=TRUE、新 DTSTAMP、保留 UID）
  • 自带递归引擎：ev.Occurrences(from,to,limit)、ParseRRule("FREQ=MONTHLY;BYDAY=-1FR").Between(...)
  • FreeBusy(events,from,to) 返回 busy 区间与 free 空隙两段
  • 时区态度成熟：UTC / floating / TZID / VALUE=DATE 全处理，并专门处理"date-only 值错误带了 TZID"这一现实 quirk —— 忽略而非悄悄挪一天
  • 只依赖 arran4/golang-ical；从 matcha 邮件客户端的会议邀约卡片中抽出来
缺口（自报） BYWEEKNO / BYYEARDAY 解析但展开时忽略；不做 CalDAV

emersion/go-webdav Go

WebDAV / CalDAV / CardDAV 客户端＋服务端 · MIT
  • 包文档一句话："Package caldav provides a client and server CalDAV implementation. CalDAV is defined in RFC 4791."
  • 完整的 filter 树：CompFilter / PropFilter / ParamFilter / TextMatch，含 IsNotDefined、NegateCondition、Start/End 时间范围，并有服务端侧 Match() 与 Filter()
  • CalendarCompRequest 支持按属性与按子组件裁剪（AllProps / Props / AllComps / Comps 嵌套）；v0.7.0 起有 CalendarExpandRequest{Start,End}
  • 11 个 RFC 4791 §5.3.2.1 前置条件全部建了常量：no-uid-conflict、supported-calendar-data/component、valid-calendar-data/resource、calendar-collection-location-ok、max-resource-size、min/max-date-time、max-instances、max-attendees-per-instance
  • ValidateCalendarObject 按 §4.1 校验并回传唯一事件类型与 UID；CalendarObject.Data 直接是 *ical.Calendar（解析过的，不是字节）
  • 服务端侧 Backend 接口 + Handler；客户端 QueryCalendar / MultiGetCalendar / PutCalendarObject（含 IfMatch/IfNoneMatch 条件写）；DiscoverContextURL 做 DNS 服务发现（RFC 6352 §11）
缺口 caldav 包的 API 索引中未见 sync-collection / sync-token（RFC 6578）；README 极简，功能要靠读 API 面才知道

其余 Go 解析器（三家） Go

同层的差异化尝试
  • saltfishpr/ical：把 "parsing, building, validation, and serialization" 四件事并列写进自我定义，各组件各有 New* 构造器
  • mscloudx/ical：主打"高性能、最少分配"的 io.Reader 流式解析 ＋ io.Writer 编码 ＋ functional-options 构造
  • luxifer/ical：按 Rob Pike 词法扫描演讲组织的 lexer/parser，Parse(io.Reader, *time.Location)；自报 VEVENT / VTODO / VJOURNAL / VFREEBUSY / VTIMEZONE 清单
  • vareversat/gics：以"创建 VEVENT / VALARM / VJOURNAL / VFREEBUSY"的勾选清单自述
含义 Go 至少有 5 个平行实现的解析层——该层已饱和，差异化只剩校验、性能、时区态度三个轴

Go 递归层的其它尝试 Go

对 dateutil 移植版性能不满
  • stephens2424/rrule：自述写作动机是"克服此前实现的性能问题——那些实现大体上是 python-dateutil 的直接移植，算法复杂且没用上 Go 的语言特性"；v1.2.0，BSD-3，仍依赖 rrule-go v1.2.3
  • graham/rrule：自述"我找到一个库只做解析、另一个只做编辑、另一个只做展开，但没有一个三件都做"，并提供 Limit / After / Between 迭代器助手
  • julienbreux/rrule-go：改为对标 rrule.js 而非 dateutil；最低 Go 1.8
含义 同一层出现 4 个并行实现、且理由各是"性能"与"三合一"，说明这一层从未让人满意

Go 的 CalDAV 服务端 Go

数量可观但都不大
  • codanael/caldav-go：自述实现 RFC 4791 / 4918 / 5545 / 6578，VEVENT + VTODO，sync-token 与 CTag，PROPFIND / PROPPATCH / MKCOL / PUT / GET / DELETE / OPTIONS / REPORT、calendar-query；并写明已对 Apple Calendar、Apple Reminders（经 VTODO）、Google Calendar 测过兼容
  • samedi/caldav-go：提供各 CalDAV HTTP 请求的 handler 以快速搭服务端
  • lshvetsov/go-webdav：自报 If-Match / If-None-Match（RFC 7232）乐观锁、RFC 6578 增量同步、时间范围过滤、自动冲突解决
  • yinjun1991/caldav-client-go：有 SyncCalendarList / SyncCalendarListWithLimit / SyncCalendar(SyncQuery)
缺口 无 Radicale 量级的公认选项；"自动冲突解决"这类声明本轮未见其策略细节

Go 终端日历 App 群 Go

6 个，功能口径趋同
  • chroncal：终端优先的日历＋待办＋日记，SQLite 本地存储，iCal 导入导出，CalDAV 同步，TUI 月/周/日/agenda 四视图 ＋ 可脚本化 CLI（事件、todo、journal、告警、free/busy 查询）
  • TipiCal：CalDAV 同步（Nextcloud / Google / iCloud）、day / 3-day / week / month / agenda 五视图、含递归与提醒的事件富编辑器、Vim 键位、可主题化
  • vimalender v1.0.1：Bubble Tea + Lip Gloss 的 vim 风格，导航/新建/移动/搜索/自定义，另附非交互子命令（含导入 .ics）供脚本调用
  • kkga/tdx：面向 vdirsyncer vdir 格式的 todo 管理器，自动日期与优先级解析，可当 iOS Reminders / Tasks.org 的 CLI 伴生
  • samuelstranges/chronos：vim 键位＋visual mode，week 视图可调缩放（30/15/5/1 分钟），事件的增删改与复制粘贴、递归事件、多日历、基于 iCal 的实验性同步
  • NStefan002/tui-calendar：Google Calendar 同步（OAuth）
含义 这批项目共同勾勒出"日历 CLI/TUI 的功能及格线"，是 moon-ical 最直接的对照面
卡片里最值得记住的三条： 一，khal 把 Features 一节副标题写成 "(or rather: limitations)"，并承认不能编辑事件时区—— 一个成熟的终端日历在时区编辑上仍是缺的； 二，Radicale 明说"只实现到能让客户端理解为止"，这是以现实互操作而非规范完整性为验收标准的范例； 三，Go 终端 App 群里有三个（chroncal / TipiCal / yinjun1991 客户端）都把 free/busy 与 sync-token 列进卖点，说明这两项在用户侧已被当作"应该有"。
