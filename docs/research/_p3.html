Python 社区自己把这件事称为 "Python Calendaring Ecosystem"（pycal.org，取自 icalendar README 的"相关项目"一节）。那份列表里有若干胶水型小库值得注意：x-wr-timezone （专治 Google 私有 X-WR-TIMEZONE 的库＋CLI）、icalendar-compatibility （"以兼容 RFC 5545 与不同实现的方式读取事件数据"）、ics-query（命令行查询 .ics 中的实例）、 ical2jcal、icalendar-anonymizer（剥离隐私字段以复现 bug）。

这些胶水库的存在本身就是结论。当一个生态需要单独一个包处理"Google 导出文件的时区语义"、 单独一个包做"跨实现读取兼容"、单独一个 CLI 做"查某天有哪些实例"时，说明这些能力没有被任何主流库吸收。 它们正是真实用户会撞上、而库里没有的活。

Go 侧最结构性的一条事实来自 arran4/golang-ical README 原文： "This library parses and provides typed access to recurrence properties (RRULE, RDATE, EXDATE, EXRULE, RECURRENCE-ID) but does not expand them into concrete occurrence dates. This keeps the library dependency-free and lets callers choose their own expansion strategy." 即：事实标准解析库刻意不做递归展开。其 README 给出的展开示例直接依赖 teambition/rrule-go， 并附带一段需调用方手写的 RECURRENCE-ID 覆盖表（按 UID＋起始时间建 map，命中则替换或删除实例）—— 这段样板是以"你该这么做"的形式出现在 README 里的，而不是库替你做好。

同页另一条细节属于典型的"规范与现实冲突"：该库 .Serialize() 默认输出 LF 换行， 要符合 RFC 5545 要求的 CRLF 必须显式传 ics.WithNewLineWindows，README 措辞是 "否则 Outlook、Apple Calendar 等客户端可能不认"。默认值选了合规性更差的一边，把兼容风险留给调用方—— 这是可以直接当反面教材的地方。

还有一条来自 luxifer/ical 的实现路线证据：它按 Rob Pike《Lexical Scanning in Go》的 lexer/parser 流水线组织，Parse(r io.Reader, l *time.Location) 显式把 *time.Location 作为解析入参——即把"用哪个时区解释无 TZID 的值"这个决策暴露在函数签名上。 对比 arran4 的属性袋模型，这是对待时区歧义的两种截然不同的态度。
